# Structure

A screen is built from four kinds of thing - a *screen*, its *layout*, that layout's *regions*, and the *blocks* drawn in them. Each kind owns a fixed set of capabilities, and owns them alone.

That last part is what makes the model useful. When something doesn't obviously fit - a new kind of block, a feature that could live in two places - the question is never "where does this go", it's **which level owns the capability it needs**. The answer follows.

## The hierarchy

Four levels, and nothing else:

```
Screen        the root; fills the terminal, or fits its contents
└─ Layout     arranges; reusable by name
   └─ Region  holds blocks; declares whether it scrolls
      └─ Block   drawn in a region
```

One kind of block - a *panel* - contains a *layout*, which starts the chain again. That's where depth comes from, rather than from a fifth level:

```
Screen
└─ Layout                      'three-region'
   └─ Region                   'content'
      └─ Block                 a Panel
         └─ Layout             'two-column'
            └─ Region          'left'
               └─ Block        a Field
```

Nothing holds a *field* except a *region*. A field is a block, so it's placed exactly as any other block is: a panel doesn't contain fields, it contains a layout whose regions do.

## Levels, kinds and instances

The four levels are what the model is made of. What you actually build with are *kinds* of each, and what ends up on screen are *instances*:

| Level | Kinds | Instances, on the screen below |
|---|---|---|
| Screen | one | the screen |
| Layout | `three-region`, `two-column`, … | the screen's `three-region` |
| Region | none - a layout names its own | `header`, `content`, `footer` |
| Block | Panel, Field, Markup, Breadcrumb, KeyHints, Buttons, Progress | one Breadcrumb, one Panel, three Fields, one KeyHints |

*Layouts* are the level with reusable named kinds - that's what *Reuse* means in the table below. *Regions* have no kinds at all: a region is a named slot its layout declares, so `header` exists because `three-region` says so.

The rows in the next table mix the two: the first three are levels, and the seven after them are kinds of block.

## Capabilities

Sixteen capabilities cover everything on screen, each described as what you can observe rather than how it's built.

| Capability | What's possible |
|---|---|
| **Act** | Activating it does something, rather than revealing something. |
| **Advertise** | It says which keys apply while it's in play. |
| **Answer** | It holds a value that ends up in the result. |
| **Arrange** | It decides where the things inside it sit. |
| **Contain** | Other things appear inside it. |
| **Enter** | You go into it: the screen becomes its contents, the trail grows, and you can come back. |
| **Expand** | It opens in place to collect something, then closes again. |
| **Expect** | It says what it will accept, before you act. |
| **Fill** | It expands to the whole terminal, instead of fitting its contents. |
| **Float** | It draws over everything else. |
| **Focus** | You can move onto it, and your keys then act on it. |
| **Refuse** | It can reject what you gave it, and say why. |
| **Reuse** | One definition, used in more than one place. |
| **Scroll** | Its contents can outrun its space, and you can move through them. |
| **Show** | It draws something you can read. |
| **Vary** | It appears or disappears depending on other answers. |

Seven readings of that table are worth stating outright, because they're the ones a new block will test.

**Only a field answers.** Everything else on screen shows, focuses or acts, and none of it reaches the collected result.

**Focus and Act come apart.** A *progress* block takes the cursor and runs work while answering nothing. *Markup* does neither. A *field* focuses and answers but never acts.

**Arrange belongs to the layout alone.** A *panel* doesn't arrange anything - it *contains* a layout, and the layout arranges. That's what lets one layout serve a panel and a screen without either knowing about the other.

**Scroll belongs to the region.** A layout is composed of region instances, and each declares whether it scrolls. So one layout can pin a column and scroll its neighbour, with the decision sitting where the scrolling is seen.

**Fill belongs to the screen.** Whether the frame takes the whole terminal or shrinks to its contents is a property of the root, not of any layout inside it - so a layout behaves the same either way.

**A panel shows and focuses only when nested.** A sub-panel is a row you select to enter. The panel currently filling the screen draws no row of its own and takes no cursor; its blocks do.

**Formatting is not a capability.** *Markup* renders as plain lines, as a bordered card, or as a table of rows and headers, and none of that changes what it can do. A table is markup laid out as a table, so it needs no row of its own. Capabilities say what a block can do; the theme says what it looks like doing it.

## Screen

The **screen** is the root. It holds one *layout* and claims one capability of its own - *Fill*:

```php
(new Tui($form))->fullscreen()->run();
```

*Fill* sits here rather than on a layout because it's a fact about the terminal, not about any arrangement inside it. A layout behaves identically whether the frame stretches to the terminal or shrinks to its contents, which is what makes a layout portable between the two.

## Layout

A **layout** is composed of *region* instances, and it decides where they sit. It claims *Arrange*, *Contain* and *Reuse*.

*Reuse* is the point: a layout is named and reusable, so the same one serves a *screen* and a *panel*. The library ships several, and a form picks one rather than describing an arrangement inline.

A layout draws nothing. That's what separates it and *region* from every *block*: neither claims *Show*.

## Region

A **region** is a named area of a *layout*. It claims *Contain* and *Scroll*.

*Scroll* is declared per region instance, not per layout, which is why a two-column layout can pin one column while its neighbour scrolls. The region declares it and the region is where you see it.

A region knows only that it holds blocks. It never knows which kinds.

## Block

A **block** is anything drawn in a *region*. That's the whole definition: it fills the space it's given, and the region knows nothing else about it.

Every block claims *Show*, and only a *panel* holds anything - so a block never contains a field, or another block. Seven kinds exist:

- **Panel** - contains a layout; entered and left. The only block you navigate into.
- **Field** - answers. The only block that reaches the collected result.
- **Markup** - renders formatted content: prose, a bordered card, or a table.
- **Breadcrumb** - renders the trail of panels you've entered.
- **KeyHints** - renders the keys that apply right now, rewriting itself as focus moves.
- **Buttons** - submits or cancels the form.
- **Progress** - runs work when activated, showing an indicator while it runs.

The last four are the ones easily mistaken for chrome. They aren't: a *breadcrumb* is a block in the header region and a *KeyHints* is a block in the footer region, placed exactly as a *field* is placed. Which is why either can be moved, or joined by something else, without a new concept.

## Panel

A **panel** is the busiest *block*:

```
Panel  "Delivery"
├─ Show       as a nested row: its title and a summary of its contents
├─ Focus      as a nested row: the cursor lands on it
├─ Enter      going in replaces the screen and grows the trail; leaving restores both
├─ Contain    it holds a layout, whose regions hold its blocks
├─ Float      as a modal, it draws over the dimmed screen behind it
└─ Advertise  its keys fill the legend while you're in it
```

**Enter is the capability nothing else has**, and it's what makes a panel more than a container. A *region* can hold blocks and a *layout* can arrange them, but neither is somewhere you go.

One panel fills the screen at a time. A **modal** is the same block that *Floats* instead of replacing what's behind it - nothing else about the panel changes.

## Field

A **field** is the *block* that answers. It's the only kind that contributes to the collected result, and the only kind that expands.

One field owns both modes. In **view** mode it's one line, drawing every part of that line itself. Open it and it switches to **edit** mode, taking over the region right of its *label*:

```
view mode    ❯ Basket contents ⁱ  apple, carrot
                                  └─────┬─────┘
                                    the settled value

edit mode    ❯ Basket contents    ● Apple
                                  ○ Carrot
                                  └───┬───┘
                                    the field collecting it
```

The *label* and the *selector* stay put across both. Only the *value* region changes shape, which is why a field in *edit* mode is still one row of its *panel* rather than something new on the screen. [Anatomy](/widgets/anatomy) names every piece of both.

*Expect* and *Refuse* are two capabilities rather than one because they answer different questions. *Expect* states what the field will accept before you act; *Refuse* explains why what you did was rejected. They share one line on screen and never appear together.

Between the field and the theme sit its **capabilities** - the shared behaviour a field draws on rather than reimplements. The chain runs one way and never doubles back:

```
Field  ──▸  capabilities  ──▸  theme templates  ──▸  theme elements
```

## Markup

**Markup** renders formatted content and does nothing else. It takes plain text or the [markdown subset](/markdown), and it claims *Show* and *Vary*. How it's laid out on the page is a presentation choice rather than a capability:

```php
$p->markup('weighing', 'Every crate is weighed at the packing bench.');
$p->markup('yields', 'Yields per crate')->table(['Produce', 'Crates'], [['Apple', '12'], ['Carrot', '8']]);
```

Prose, a bordered card and a table are the same block laid out three ways. *Vary* is what lets a warning appear only when an earlier answer calls for it.

## The theme's two tiers

An **element** is the smallest styled piece. It takes a plain string, returns a styled one, and knows nothing about what surrounds it:

```
Orchard  ›  Delivery
───┬───  ┬  ────┬───
   │     │      └── breadcrumbLabel()
   │     └───────── breadcrumbSeparator()
   └─────────────── breadcrumbLabel()
```

A **template** composes elements into a block's output, deciding order, spacing and how many elements there are:

```
renderBreadcrumb(['Orchard', 'Delivery'])
        │
        ├── breadcrumbLabel('Orchard')
        ├── breadcrumbSeparator()
        └── breadcrumbLabel('Delivery')
```

Both are public, and the split tells you which to override:

| Tier | Shape | Override to |
|---|---|---|
| Element | `breadcrumbLabel(string $text): string` | change color, weight or glyph |
| Template | `renderBreadcrumb(array $segments): string` | change layout, order or what's included |

Templates are implemented on the abstract theme, so a custom theme inherits working layout and touches only the elements it wants repainted. Overriding a template is the rare case: it means changing the shape of something, not its palette.

## On screen

Here it is on a real screen, each level labelled on the row it owns - the *region*, the *block* in it, then the *panel*'s *fields* and the *mode* each is drawing:

```
                              ╭──────────────────────────────────────────────────────╮
header  ▸ Breadcrumb          │ Orchard › Delivery                                   │
                              ├──────────────────────────────────────────────────────┤
content ▸ Panel               │                                                      │
          ▸ Field  edit mode  │ ❯ Basket  ● Apple                                    │
                              │           ○ Carrot                                   │
                              │     Pick the produce.                                │
                              │                                                      │
          ▸ Field  view mode  │   Basket weight  1200                                │
                              │                                                      │
          ▸ Field  view mode  │   Harvest date  2026-07-15                           │
                              │                                                      │
                              │   ▼                                                  │
                              │                                                      │
                              ├──────────────────────────────────────────────────────┤
footer  ▸ KeyHints            │ ↑/↓ to move · ↵ to accept · ESC to cancel             │
                              ╰──────────────────────────────────────────────────────╯
```

The `header` and `footer` *regions* declare no *Scroll*, so they're pinned; `content` declares it, which is why the mark under `Harvest date` belongs to that region rather than to the frame. The `Basket` *field* is open, so it's in *edit* mode: its two *entries* and its *description* all belong to that one *field*.

## Building one

The hierarchy is what's there, not what you have to type. A three-field form names none of it:

```php
$form = Form::create('Orchard')
  ->panel('main', 'Delivery', function (PanelBuilder $p): void {
    $p->text('courier', 'Courier');
    $p->number('weight', 'Basket weight')->min(200)->max(9000);
    $p->confirm('organic', 'Organic only?');
  })
  ->build();

(new Tui($form))->run();
```

Every level has a default, and this is what those defaults are:

```php
Screen::create()
  ->layout('three-region', fn(LayoutBuilder $l) => $l
    ->region('header', fn(RegionBuilder $r) => $r->add(new Breadcrumb()))
    ->region('content', fn(RegionBuilder $r) => $r->add($panel)->add(new Buttons()), scrolls: TRUE)
    ->region('footer', fn(RegionBuilder $r) => $r->add(new KeyHints())));
```

Adding *markup* between two *fields* doesn't change the shape of the code, because markup and a number are both blocks in the same region. Only one of them answers:

```php
->panel('main', 'Delivery', function (PanelBuilder $p): void {
  $p->text('courier', 'Courier');
  $p->markup('weighing', 'Every crate is weighed at the packing bench.');
  $p->number('weight', 'Basket weight')->min(200)->max(9000);
})
```

Two columns is the first thing that needs a *layout*, so it's the first thing that names one:

```php
->panel('main', 'Delivery', fn(PanelBuilder $p) => $p
  ->layout('two-column')
  ->in('left',  fn(RegionBuilder $r) => $r->text('courier', 'Courier'))
  ->in('right', fn(RegionBuilder $r) => $r->number('weight', 'Basket weight')))
```

Named regions mean a block says where it goes, rather than depending on the order it was declared in.

## Resolving a tension

When something doesn't fit, name the capability it needs and the level that owns it. Three worked examples:

**"Should markup be able to sit in the footer?"** The footer is a *region* of a *layout*, markup is a kind of *block*, and blocks are placed in regions. So yes - add the markup block to that region. It's a placement, not a feature.

**"Should a progress row appear in the result?"** It would need *Answer*, which only a field claims. No - progress *Acts*, which is a different capability.

**"Should a panel scroll its left column but not its right?"** *Scroll* belongs to the region, and a layout is composed of region instances. Yes - the left region declares it, the right doesn't, and no block changes.

The point of the split is that each of those has one answer rather than an argument. A *region* that knew what a breadcrumb was would need to know what every block is; instead a region knows only that it holds blocks, a block knows only how to fill the space it's given, and a theme knows only how to style what it's handed.

That's also what makes an element reusable. Because `breadcrumbSeparator()` receives no field, no panel and no answers, the same element draws the separator inside a form and inside a standalone line of output. An element that reached for form state could only ever be used from inside a form.
