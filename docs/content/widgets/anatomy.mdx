# Anatomy of a widget

Every field draws itself in one of two modes. In **view mode** it's a single line carrying the answer, with any supporting lines beneath it. Open it and it switches to **edit mode**, where the widget takes over the space to the right of the label and draws whatever it needs to collect the answer.

This page names each part, so a bug report can say "the constraint line is wrong" and mean exactly one thing. Each mode numbers its own parts from one, because a reader looking at one mode isn't looking at the other. Where this page crosses between them it says which - the **value** (view 6) rather than a bare number.

The names describe what you see, never how it's built. A file browser's list is captioned with the directory you're in, but the part is a **caption** (edit 11) rather than a "directory line", because the next browser to caption its list won't be showing you a directory.

Every part is drawn by a theme method - an [atom](/themes) - named after the part it draws. The tables below list them, and that mapping is the contract: a theme overriding the atom restyles the part, everywhere the part appears. Some rows are still blank, because the part is drawn inline with no atom to override yet. Those blanks are the work list.

:::note

The frames are real captured output. The vocabulary is settled; [open questions](#open-questions) tracks what isn't.

:::

## View mode

A panel stacks its fields as rows, each one in view mode until you open it. Five fields of a delivery form are visible here, with more continuing past the bottom edge.

<p align="center">
  <ThemedImage sources={{light: useBaseUrl('/anatomy-row-light-static.svg'), dark: useBaseUrl('/anatomy-row-dark-static.svg')}} alt="Five rows of a form with their parts named" width="100%" />
</p>

| # | Part | What it does | Atom |
|---|---|---|---|
| 1 | breadcrumb | The trail of panel titles. It's every panel you've descended through plus the one you're in, so it gains a segment when you open a sub-panel and drops one when you come back. | `breadcrumb()` |
| 2 | breadcrumb separator | Stands between the segments of the **breadcrumb** (1). | `separator()` |
| 3 | field selector | Which field has focus. Only one field holds focus at a time - which is why this is the one part here with a single arrow - and it moves with <kbd>↑</kbd> and <kbd>↓</kbd>; the row it's on is drawn brighter, so the glyph and that emphasis are one signal in two forms. | `marker()` |
| 4 | label | The field's name, and the one part of a row that never changes while you work. Every row has one, so the number carries an arrow per row: a part that occurs several times keeps a single number, since numbering each occurrence would read as several different parts. | `label()` |
| 5 | help marker | Sits after the **label** (4) when a field has **help** (9) to show, in the label's own colour. `Basket contents` is the only field here carrying **help** (9), so it's the only one wearing one. It hangs off the **label** (4) rather than the **description** (8), because a field can carry **help** (9) without carrying a **description** (8), and a **label** (4) is the one part every row draws. | `helpMarker()` |
| 6 | value | The settled answer. It shows what was accepted, so it stays empty until the field is answered and never shows what you're mid-way through typing - that's the **draft** (edit 9). Like the **label** (4), every row has one, so its number carries an arrow per row. | `value()` |
| 7 | value separator | Stands between the parts of a **value** (6) that has more than one. `Basket contents` holds two, so it reads `apple, carrot`. | |
| 8 | description | The field's explanatory text, under its row. Declared once on the field and shown whether or not the row has focus, so it never changes while you work. | `description()` |
| 9 | help | The field's long-form text. It's the only part not on screen: press <kbd>?</kbd> and it opens in a popup, which is what lets it run to paragraphs where a **description** (8) has to stay a sentence. | |
| 10 | overflow marker | Content continues above or below. It appears only when the rows don't fit the panel, and points the way there's more. | `indicator()` |
| 11 | legend | The keys available right now. It rewrites itself as focus moves, so a field in edit mode lists different keys from the panel around it. | `renderHintLine()` |
| 12 | legend key | One key in the **legend** (11). Worded keys are uppercased - <kbd>ESC</kbd>, <kbd>TAB</kbd>, <kbd>SPACE</kbd> - so the eye lands on what to press before reading what it does. | `legendKey()` |
| 13 | legend description | What that key does, reading as `KEY to action` so an entry is a sentence rather than two words abutted. | `legendDescription()` |
| 14 | legend separator | Stands between one **legend** (11) entry and the next. | `legendSeparator()` |

## Edit mode

Edit mode hands the region right of the label to the widget, and what the widget draws there depends on how it collects an answer. The three shapes below cover it: choosing from a list, typing, and browsing.

### Choosing from a list

A multiple-choice field with bounds and per-entry text draws the fullest set of parts.

<p align="center">
  <ThemedImage sources={{light: useBaseUrl('/anatomy-editor-light-static.svg'), dark: useBaseUrl('/anatomy-editor-dark-static.svg')}} alt="A multiple-choice field in edit mode with its parts named" width="100%" />
</p>

| # | Part | What it does | Atom |
|---|---|---|---|
| 1 | entry | One line of the list the widget offers. What fills the list varies by widget: a fixed set, a set filtered as you type, or one fetched by a query. | |
| 2 | entry selector | Which **entry** (1) has focus. It moves with <kbd>↑</kbd> and <kbd>↓</kbd>, and moving it chooses nothing on its own. | `marker()` |
| 3 | entry marker | The per-entry chosen-state glyph. It shows what's chosen, not what has focus, so it only changes when you actually pick something - <kbd>Space</kbd> in a multiple-choice list. | `check()`, `radio()` |
| 4 | entry note | A qualifier on an **entry** (1), such as why it's unavailable. It appears only on entries that carry a reason. | |
| 5 | entry description | The focused **entry** (1)'s own explanatory text. It's rewritten every time the **entry selector** (2) moves, and is absent for entries that declare none. Indented to start where the entry text starts, so it reads as belonging to the entry above it rather than to the list. | `entryDescription()` |
| 6 | constraint | What the field expects, before anything is rejected. It's there from the moment edit mode opens, and the **error** (7) replaces it the instant a value is refused. | `renderGuidance()` |

**Selecting and marking are different things.** A selector shows where you are; a marker shows what you've marked. That's why the **entry selector** (2) and the **field selector** (view 3) are the glyphs that follow your movement, while the **entry marker** (3) is the box that records a decision. Moving a selector chooses nothing.

The pairs are deliberate. The **field selector** (view 3) shows which field you're on and the **entry selector** (2) which entry within it; the **description** (view 8) is the field's own text and the **entry description** (5) an entry's. Same idea at two levels, so a parent's name is never reused for its child.

### Typing rather than choosing

Some widgets collect an answer by typing instead of by choosing from a list, so they have no **entry** (1) at all. The [Template](/widgets/template) widget shown here fills the named slots of a fixed pattern.

<p align="center">
  <ThemedImage sources={{light: useBaseUrl('/anatomy-text-light-static.svg'), dark: useBaseUrl('/anatomy-text-dark-static.svg')}} alt="A Template field in edit mode with its parts named" width="100%" />
</p>

| # | Part | What it does | Atom |
|---|---|---|---|
| 8 | caret | The insertion point within the **draft** (9). It shows where the next keystroke lands, and in the [Template](/widgets/template) widget it's what moves between slots as you fill them. | `caret()` |
| 9 | draft | The text you're typing, before it's accepted. It becomes the **value** (view 6) when you accept, and is discarded if you cancel. | |
| 10 | state | What the widget is doing right now. It tracks the widget rather than the field, so it changes as you work - here it names the slot you're filling. | `footer()` |

The **draft** (9) and the **value** (view 6) are the same answer at two moments: what you're typing, and what was accepted.

The **state** (10) is easy to confuse with the **description** (view 8), so it's worth being precise. The first tracks the widget and changes while you work; the second belongs to the field and never moves.

### Browsing a list

The [FilePicker](/widgets/filepicker) widget draws the same skeleton over a directory listing, and adds a **caption** (11) above it.

<p align="center">
  <ThemedImage sources={{light: useBaseUrl('/anatomy-filepicker-light-static.svg'), dark: useBaseUrl('/anatomy-filepicker-dark-static.svg')}} alt="An open file picker with its parts named" width="100%" />
</p>

| # | Part | What it does | Atom |
|---|---|---|---|
| 11 | caption | What the list below is showing. It's rewritten whenever the list changes underneath it, so here it names the directory you've navigated into. | `caption()` |

The lines in the list are files and directories rather than options, and they're still **entries** (1): the name describes the line the widget offers, not where its content came from. The **caption** (11) names a directory in this widget because that's what a file browser browses, but the part - and the atom that draws it - stays generic.

### Constraint and error: one line, two states

The **constraint** (6) and the **error** (7) share a single physical line. Below is one [FilePicker](/widgets/filepicker) field, limited to files of at most 64 bytes, photographed twice.

Nothing has been picked yet, so the line states what the field expects:

<p align="center">
  <ThemedImage sources={{light: useBaseUrl('/anatomy-constraint-light-static.svg'), dark: useBaseUrl('/anatomy-constraint-dark-static.svg')}} alt="A file picker showing its constraint before anything is rejected" width="100%" />
</p>

Now `harvest.csv` is picked, and at 88 bytes it breaks that limit. The same line, in the same place, turns into the **error** (7). The **constraint** (6) doesn't move down or stay above it - it's replaced:

<p align="center">
  <ThemedImage sources={{light: useBaseUrl('/anatomy-error-light-static.svg'), dark: useBaseUrl('/anatomy-error-dark-static.svg')}} alt="The same file picker showing an error in place of its constraint" width="100%" />
</p>

| # | Part | What it does | Atom |
|---|---|---|---|
| 7 | error | Why the value was rejected. It appears only after a refused accept, and clears the moment the value becomes acceptable, handing the line back to the **constraint** (6). | `error()` |

Read the two lines side by side and the distinction is the whole point:

| | Line | Says |
|---|---|---|
| **constraint** (6) | `Files only. Max 64 B.` | what the field will accept, before you act |
| **error** (7) | `Choose a file no larger than 64 B.` | why what you just did was refused |

A **constraint** (6) describes the field; an **error** (7) describes your value. That's also why they're built differently. The first is an unframed phrase - `a file no larger than 64 B` - that its caller wraps, so the same phrase becomes `Choose ...` in the picker, `Select ...` in a bounded list and `must be ...` headlessly. The second is already a whole message, and is shown as it stands.

## Where the names disagree

**An atom is named after the part it draws.** `Field::$label` and `ThemeInterface::label()` line up because a theme's vocabulary should be the vocabulary a reader uses for what's on screen. Where the code and this page disagree on a name, the code is what moves.

**`hints()` returns the legend, not a hint.** `WidgetInterface::hints()` has nothing to do with `Field::$hint` or with `ThemeInterface::hint()` - it returns the keys of the **legend** (view 11). It becomes `WidgetInterface::legend()`.

**`hint` will name one thing.** `Field::$hint` becomes `Field::$help`, since its text is the **help** (view 9) and belongs in the popup rather than on a line under the row. That leaves `ThemeInterface::hint()` drawing exactly one part, the **constraint** (edit 6), so the atom takes that name too.

**`marker` covers two levels.** The **field selector** (view 3) and the **entry selector** (edit 2) are both `ThemeInterface::marker()`, so a theme can't restyle one without the other - and neither is a marker any more.

**The entry marker answers to two names.** It's `ThemeInterface::check()` in a multiple-choice list and `radio()` in a single-choice one, so which atom draws it depends on the widget rather than on the theme.

**`error` names four things.** `ThemeInterface::error()` is a style atom, `WidgetInterface::error()` is widget state, `Field::templateError()` and friends produce a message, and `Engine::optionsError()` builds an exception.

**`footer` is drawn outside the footer.** The **state** (edit 10) uses `ThemeInterface::footer()`, which otherwise styles the **legend** (view 11) at the bottom of the frame.

**The separators aren't named as a pair.** The **breadcrumb separator** (view 2) is `ThemeInterface::separator()`, which reads as the only separator there is, and the **value separator** (view 7) is hardcoded in `ValueFormatter::format()` with no atom at all.

## Open questions

Working notes, kept here only until each one is settled.

**Should the entry marker be one atom?** It's two today - `check()` for a multiple-choice list and `radio()` for a single-choice one - picked by the widget rather than by the theme. One `entryMarker()` that flips between them would put the whole part in a theme's hands at once.

**Should the field selector and the entry selector be separate atoms?** They're one method today, so a theme can't restyle the field cursor without also restyling the one inside every list. They're named as a parent/child pair, which argues they should be stylable as one.

**Should the entry get an atom of its own?** The **entry** (edit 1) is drawn inline today, so it can't be restyled without overriding the whole list renderer. The **entry note** (edit 4) and the **draft** (edit 9) are in the same position.

**Should the state stop borrowing `footer()`?** The **state** (edit 10) is drawn with the atom that styles the **legend** (view 11) at the bottom of the frame, which is a different part in a different place.

**What replaces the keyboard overlay?** <kbd>?</kbd> currently opens a list of every widget type's keys, which is being dropped in favour of the **help** (view 9) popup - the **legend** (view 11) already shows the keys that apply right now, and rewrites itself as focus moves. Worth confirming nothing is lost with it.

**Why doesn't the legend advertise <kbd>Space</kbd> in a multiple-choice list?** The frame above shows `↑/↓ move · ↵ accept · esc cancel`, with nothing for the key that actually picks an entry. The widget does report it - `SelectionCapableTrait::hints()` returns a `select` hint for `Action::Toggle` ahead of everything else, precisely because toggling is the non-obvious action - and the atom resolves it: `keysHint()` renders `space select` when asked. So the hint is produced and can be drawn, but doesn't reach the **legend** (view 11). Same for `none/all`.

**Can the help marker be a single glyph?** `[?]` is three characters because every enclosed question mark fails one way or another: `⍰` has no glyph in the monospace stack and renders as a missing-character box, while `ⓘ` and `ℹ` are naturally wider than one cell and get squeezed out of shape by a surface that pins each cell to a fixed advance.
